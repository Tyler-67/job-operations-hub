Built/maintained by us, sold white-label through one reseller (Uptiq). Supabase is the source of truth; Uptiq (GoHighLevel/LeadConnector under the hood) handles contacts, SMS/email, calendar, tags.

## Gotchas
- **`_shared/notifications.ts` edit → redeploy `cron-drain-notifications`** (it bundles that file) AND any function that enqueues the changed template
- Editing any `_shared/*.ts` → every function that bundles it must be redeployed (each function snapshots its imports at deploy time). When in doubt, redeploy all 25 (preserve `verify_jwt`: only the 4 `cron-*` are false)
- **Uptiq token / secret changes:** edge functions read secrets at BOOT, so after `supabase secrets set <X>=...` you must redeploy the function that reads it (or wait for instance recycle). Sends need the token's Conversations/Messages WRITE scope; user-lookup works on a read-only token (so login can work while sends 401)
- **pg_cron `job_run_details.status='succeeded'` ≠ function returned 200** — it only means the `net.http_post` dispatch ran. To see real status: `net._http_response` (by request id) or analytics `function_logs` (Deno stack/console) / `function_edge_logs` (METHOD|status|url) via `POST /v1/projects/<ref>/analytics/endpoints/logs.all`
- **Analytics `logs.all` (function_edge_logs/function_logs) is UNRELIABLE here** (2026-06-15): the endpoint returned `{"result":[]}` even for `invoice-paid` traffic generated seconds earlier — so an empty result is NOT proof of "no traffic." For ground truth on whether a function ran, query the persisted DB instead via `POST /v1/projects/<ref>/database/query`: `event_log` (handlers insert a row per request), `action_tokens`, `scheduled_notifications`, etc. Don't draw conclusions from an empty edge-log result.
